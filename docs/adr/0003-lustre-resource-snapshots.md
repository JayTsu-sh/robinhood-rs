# 以资源快照解耦 Lustre 采集和控制台查询

Lustre 资源观测负责记录已注册文件系统的挂载、池成员和容量。`scheduler-rs` 周期触发采集，采集结果按采集端和文件系统 ID 原子保存到 MariaDB。控制台从数据库读取本采集端最近的资源快照。这让页面读取时间与 Lustre 客户端的响应时间分离，并保留 daemon 重启前的观测结果。

Lustre 集群列表和详情页通过 `GET /api/filesystems/events` 订阅 daemon 的 SSE 通知。快照入库后发送 `snapshot` 事件，注册或管理状态变更可读后发送 `management` 事件，数据为文件系统 ID。每次定时采集开始时也发送数据为 `*` 的 `management` 事件，触发外部挂载信息的重新读取。通知队列溢出时发送 `resync`，页面在收到此事件或重新连接时补读当前数据。收到通知和点击重试时，页面都通过现有的查询接口读取数据。手动采集仍可通过 REST 接口发起。

## 领域规则

- `FileSystemId` 来自部署注册。分层策略通过 ID 引用文件系统，资源快照服务于运维查看。保存、启用和执行分层策略时继续使用策略引擎的现场校验。
- 文件系统容量汇总已登记的唯一 OST，包含池外 OST。池容量按各自成员汇总。缺失成员容量时标明采集状态，完整的历史样本保留原采集时间。经确认的空池容量为零。
- 资源快照随每次采集更新，携带最近尝试时间及可用样本。匹配当前挂载与池成员时，失败的采集可以展示过期样本。分层可用性保留挂载、能力及池成员的判断依据。

## 模块职责

| 模块 | 职责 |
| --- | --- |
| 资源观测 | 定义资源快照、容量样本和聚合规则，协调采集和保存。 |
| Lustre 采集 | 从对应的客户端挂载取得池成员和每个 OST 的测量结果。 |
| MariaDB 快照存储 | 保存和读取每个已注册文件系统的最近观测及可复用的完整样本。 |
| scheduler-rs 与 REST | 定时任务、手动全量刷新和手动单资源刷新共用采集用例。查询接口只读取已保存的快照。 |

验证覆盖定时采集在无页面请求时更新数据库、按文件系统隔离刷新、重启读取已保存快照，以及异常 OST 对其他资源和池的影响。 [#26](https://github.com/JayTsu-sh/robinhood-rs/issues/26)
